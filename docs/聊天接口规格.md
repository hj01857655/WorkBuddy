# WorkBuddy 聊天接口规格（OpenAI 兼容 · SSE 详解）

> **本机实测 + 官方产物逆向双证据**。基准环境：WorkBuddy **5.6.2**（Windows），
> 账号 `887e22c0-32df-4935-8811-226031b6d12d`（CN / `www.workbuddy.cn`）。
> 本文所有「实测」标注均指 2026-09-26 本机真实请求的结果，未实测的会明确标出。
>
> ⚠️ 非公开接口。请只用于你自己的机器、你自己的登录态、你自己的账号。

## 一、TL;DR

| 项 | 值 |
| --- | --- |
| 端点 | `POST https://copilot.tencent.com/v2/chat/completions` |
| 协议 | OpenAI Chat Completions 兼容 |
| **必须流式** | `stream: true` 是**硬要求**；不传 → `400 / code 11101` |
| 鉴权 | `Authorization: Bearer <accessToken>` |
| 流格式 | SSE（`text/event-stream`），`chunked` 传输 |
| 最小可用头 | **仅 `Authorization` + `Content-Type`**（实测 200） |
| 特有字段 | `delta.reasoning_content`（思维链）、`usage.credit`、`usage.completion_thinking_tokens` |
| 收尾 | `finish_reason: "stop"` 的帧**内联** `usage`，随后 `data: [DONE]` |

## 二、端点与 URL 归一化

### 2.1 上游地址

| 环境 | 上游 |
| --- | --- |
| CN（本机，实测可用） | `https://copilot.tencent.com/v2/chat/completions` |
| global | `https://www.workbuddy.ai/...`（以 `X-Domain` 为准，先试 `/console/chat/completions`，404/405 再回退 `/v2/chat/completions`） |

出处（WorkBuddy 自身产物 `app.asar`，`packages/agent-harness/computer-use/vlm/vlm-upstream.ts`）：

```js
var CHAT_COMPLETIONS_PATH = "/v2/chat/completions";
/** 默认公网网关；正常装配会通过 getGatewayEndpoint 动态跟随当前环境。 */
var DEFAULT_COMPUTER_USE_VLM_UPSTREAM_URL =
  "https://copilot.tencent.com/v2/chat/completions";
```

### 2.2 网关根地址 → chat 地址的**幂等**归一化

官方实现（同模块 `buildComputerUseVlmUpstreamUrl`），**照抄即可避免重复拼接**：

```js
function buildComputerUseVlmUpstreamUrl(endpoint) {
  const url = new URL(endpoint);
  const trimmedPath = url.pathname.replace(/\/+$/, "");
  if (trimmedPath.endsWith(CHAT_COMPLETIONS_PATH)) url.pathname = trimmedPath;
  else if (trimmedPath.endsWith("/v2")) url.pathname = `${trimmedPath}/chat/completions`;
  else url.pathname = `${trimmedPath}${CHAT_COMPLETIONS_PATH}`;
  return url.toString();
}
```

> 注释原话：幂等是硬要求 —— `getGatewayEndpoint()` 在不同装配下可能已带上 `/v2`
> 或整条 `/v2/chat/completions`，重复拼接会得到
> `/v2/chat/completions/v2/chat/completions`。

**文件里的 baseline 头**：官方代理还会强制 `Accept-Encoding: identity`
（`headers.set("Accept-Encoding", "identity")`），理由是 SSE 不能被压缩缓冲。

## 三、鉴权

```http
Authorization: Bearer <accessToken>
```

- 令牌来源与刷新见《认证与签到协议》第五、十节（本机可从桌面端登录态引导，`refreshToken` 可自动续期）。
- **无令牌 → `401`**，且响应是 **HTML 而非 JSON**（openresty / APISIX 网关层拦截，未进业务）：
  ```html
  <html><head><title>401 Authorization Required</title></head>
  <body><center><h1>401 Authorization Required</h1></center>
  <hr><center>openresty</center>...</html>
  ```
  → **客户端必须按 `Content-Type` 判分支**，不能无脑 `JSON.parse`。
- 令牌失效时官方代理的做法：**上游 401 → 刷新 → 换新 token 重试一次**；
  刷新失败则**把首个 401 原样透传**（不自造错误，以免丢掉网关侧的真实原因）。

## 四、请求头

### 4.1 官方完整头集（来自 `applyGatewayHeaders` + `buildComputerUseVlmGatewayHeaders`）

官方注释把四组的分工写得很清楚，**分组本身就是判据**：

| 组 | 头 | 取值 | 为什么 |
| --- | --- | --- | --- |
| **协商** | `Accept` | `application/json` | 一方 `/v2/chat/completions` 只收 JSON |
| | `Content-Type` | `application/json` | 同上 |
| | `x-requested-with` | `XMLHttpRequest` | **网关的准入约定** |
| **会话**<br>（一次会话内**必须稳定**） | `X-Conversation-ID` | `sessionId` | 现生成会把同一次操作的几十次调用<br>在网关侧**拆成几十个会话** |
| | `X-Conversation-Request-ID` | 会话级元数据 | |
| | `acp-connection-id` | 会话级元数据 | |
| **请求**<br>（逐请求生成） | `X-Conversation-Message-ID` | `crypto.randomUUID()` | 它们本来就该逐请求不同 |
| | `X-Request-ID` | `crypto.randomUUID()` | |
| | `X-Agent-Intent` | `"craft"` | |
| | `X-Agent-Purpose` | `"conversation"` | |
| | `x-codebuddy-request` | `"1"` | |
| **产品身份**<br>（缺了才兜底） | `X-Product` | `deploymentType` ‖ `"SaaS"` | 兜底值只保证「字段在」，<br>不代表真实环境 |
| | `X-IDE-Type` / `X-IDE-Name` | `WorkBuddy` | |
| | `X-IDE-Version` | appVersion（本机 `5.6.2`） | |
| | `X-Private-Data` | `"true"` | |
| | `User-Agent` | `WorkBuddy/<ver> WorkBuddy/<ver> [CLI/<ver>]` | |

**trace 三件套共享同一个 traceId**（`applyTraceHeaders`）：

```js
const traceId = crypto.randomBytes(16).toString("hex");
const spanId  = crypto.randomBytes(8).toString("hex");
const parentSpanId = crypto.randomBytes(8).toString("hex");
headers.set("traceparent", `00-${traceId}-${spanId}-01`);
headers.set("b3", `${traceId}-${spanId}-1-${parentSpanId}`);
headers.set("X-B3-TraceId", traceId);
headers.set("X-B3-ParentSpanId", parentSpanId);
headers.set("X-B3-SpanId", spanId);
headers.set("X-B3-Sampled", "1");
headers.set("X-Trace-ID", traceId);
```

> 注释原话：*「三套各生成一个的话，网关侧三条链路对不起来，等于没有 trace。」*

另有两个账号相关头，**登出/切账号时须清掉**（官方 `buildComputerUseVlmGatewayHeaders`
是**条件设置**，不是无条件）：

```js
if (context.userId?.trim())   headers["X-User-Id"] = context.userId.trim();
if (context.enterpriseId?.trim()) {
  headers["X-Enterprise-Id"] = context.enterpriseId.trim();
  headers["X-Tenant-Id"]     = context.enterpriseId.trim();
}
if (context.domain?.trim())   headers["X-Domain"] = context.domain.trim();
```

### 4.2 这些头**不是**网关准入必需（实测）

| 头集 | 实测结果 |
| --- | --- |
| **仅 `Authorization` + `Content-Type`** | **HTTP 200**，正常出 5 个 chunk |
| + `x-requested-with` | HTTP 200 |
| + `Accept: text/event-stream` | HTTP 200 |
| + `X-User-Id` + `X-Domain` | HTTP 200 |
| 全套（含 `X-Product`/`X-IDE-*`/trace） | HTTP 200 |

**结论**：
- **网关准入只看 `Authorization`**；`X-User-Id` 缺失也不影响 —— 服务端用令牌解析账号
  （响应头里会**回显** `X-User-Id: 887e22c0-…`，可自证）。
- 其余头是**归属与可观测性**用途：不给不会失败，但会让网关侧的会话被拆散、
  trace 断链、产品侧统计失真。**建议按官方全量携带**，只是别把它当成「不带头就 401」的原因。

## 五、请求结构

### 5.1 顶层结构（TypeScript 风格定义）

```ts
interface ChatRequest {
  model: string                        // 必填
  messages: Message[]                  // 必填，非空
  stream: true                         // 必填，且必须为 true（布尔字面量）
  temperature?: number                 // 采样温度
  top_p?: number                       // 核采样
  max_tokens?: number                  // 最大输出 token（含思维链）
  n?: number                           // 候选数
  stop?: string | string[]             // 停止词
  seed?: number                        // 随机种子
  top_k?: number
  frequency_penalty?: number
  presence_penalty?: number
  user?: string
  logprobs?: boolean
  top_logprobs?: number
  response_format?: { type: "json_object" | "json_schema", json_schema?: object }
  tools?: Tool[]                       // ← 实测可用，见 6.12
  tool_choice?: string                 // ← 只接受字符串！传对象必 400
  stream_options?: { include_usage?: boolean }
}

interface Message {
  role: "system" | "user" | "assistant" | "tool"
  content: string | ContentBlock[]     // 两种形态都实测通过
}

interface ContentBlock {
  type: "text" | "image_url"
  text?: string                        // type="text" 时
  image_url?: { url: string }          // type="image_url" 时
}

interface Tool {
  type: "function"
  function: {
    name: string
    description?: string
    parameters: object                 // JSON Schema
  }
}
```

### 5.2 字段必填性与实测状态

| 字段 | 类型 | 必填 | 实测结果（**接受 ≠ 生效**，见下方效力复核） |
| --- | --- | --- | --- |
| `model` | string | **是** | 生效：未知模型 → `400 / 11102` |
| `messages` | array | **是** | 生效：空数组 → `400 / 11133`（`extError.param = "messages"`） |
| `stream` | boolean | **是，且须 `true`** | 生效：不传 → `400 / 11101` |
| `temperature` | number | 否 | ✅ **真被消费**：高熵题下 `=0.0` 连 5 发得同一值（743），`=1.0` 出现分歧 |
| `max_tokens` | number | 否 | ✅ **生效但按后端分裂**：`auto` 上 `=20` → `finish=length, ct=20`；`hunyuan-chat` 上 `=12` 能跑到 `ct=92` |
| `tools` | array | 否 | ✅ **200 且真的触发函数调用**，见 6.12；`enum`/`required`/`additionalProperties` 实测被遵守（越界时宁可不带工具） |
| `reasoning_effort` | string | 否 | ✅ **生效（2026-10-10 补测）**：`max` 使 `completion_thinking_tokens` 429→748（auto）、0→638（glm-5.3-flash）；非法值不报错。档位见 `models[].reasoning.supportedEfforts` |
| `top_p` | number | 否 | ⚠️ **接受但无效**：`temperature=1.0` 基线 uniq=2，加 `top_p=0.0001` 仍 uniq=2（真生效应收敛） |
| **`n`** | number | 否 | ⚠️ **接受但被忽略**：`n=2` 也是 `200`，但响应 `choices` **恒为 1 项、`index` 恒为 0**（见 6.13） |
| `stop` | string \| array | 否 | ❌ **接受但不截断**（2026-10-10 行为实测）：要求输出 `###` 时，`stop=["###"]` 仍返回含 `###` 的全文（两个后端均如此）。键**在**结构体（`stop=12345` → `400 unmarshal`）但不受用 |
| `seed` | number | 否 | ❌ **无效且不在结构体**：`temperature=1.0, seed=777` 两发 `47`/`42`；`seed="字符串"` 也不报错 |
| `top_k` | number | 否 | ❌ **不在结构体**（`top_k="abc"` 不报错） |
| `logprobs` / `top_logprobs` | boolean / number | 否 | ❌ **不在结构体**；响应里 `choices[].logprobs` 只是**恒为 `null` 的空壳** |
| `response_format` | object | 否 | ❌ **不在结构体、无约束力**：`{"type":"json_object"}` 下仍返回带 ```` ```json ```` 围栏的 markdown 散文，`json.loads` 失败（旧版本本节写的「✅ `json_object` 200」只是没报错；`json_schema` 仍未测） |
| `frequency_penalty` / `presence_penalty` | number | 否 | 🔶 **在结构体、效力不稳定**：`=-2` 使输出 83→197 字（去重比 0.084→0.223），但 `=+2` 两轮与基线完全一致——不能归入「已验证」 |
| `user` | string | 否 | 在结构体（`user={…}` → `400 unmarshal`），但无可观测效应 |
| `max_completion_tokens` | number | 否 | ❌ **不在结构体**（OpenAI 已把 `max_tokens` 标废弃，但本上游只认旧名）：`=20` → `ct=277 finish=stop` |
| `parallel_tool_calls` / `logit_bias` / `modalities` / `audio` / `store` / `metadata` / `safety_identifier` / `web_search_options` | — | 否 | ❌ **不在结构体**（除 `logit_bias`/`prediction` 在） |
| `tool_choice` | **string** | 否 | ⚠️ **只接受字符串**，传对象必 `400`；**且取值支持面按后端分裂**：`hunyuan-chat` 收 `auto`/`none` 但 `required`/非法值 → `500 tool_choice invalid`；`auto` 连非法值都 200（根本不读） |
| `stream_options.include_usage` | object | 否 | 接受，但**默认就有 usage**，开了无差别 |
| `messages[].role` | string | — | `system` / `user` / `assistant` / `tool` 均实测通过（多条 `system`、`system` 不在首位也 200） |
| `messages[].content` | string \| array | — | 两种形态都实测 200；`image_url` 形态被收但能否识图取决于模型 |

#### 5.2.1 效力复核（2026-10-10，详见 `docs/workbuddy-24-协议翻译完整性审计.md`）

**上游把 body 反序列化进一个固定 Go 结构体**，实测行为三类：

1. 结构体外的键 → **静默丢弃**（`probe_zzz=1` 也 `200`）；
2. 类型不符 → `400 / 11101 Unmarshal chat params failed: cannot unmarshal … into Go struct field <Request.x> of type …`；
3. 取值非法 → **一律默许**（`max_tokens=-10`、`temperature=-5`、`top_p=99`、`penalty=999`、`seed=-7`、`n=-5` 全部 `200`）。

所以：**`200` 只证明接受性，不证明被读，更不证明被执行**。判定一个参数得看可观测行为差异。
按此定出的结构体成员表（逐字段类型非法探测，28 项）：

| 在结构体（13） | 不在结构体（15） |
| --- | --- |
| `model` `messages` `stream` `temperature` `top_p` `n` `stop` `presence_penalty` `frequency_penalty` `user` `logit_bias` `prediction` `reasoning_effort` | `agent` `top_k` `seed` `logprobs` `response_format` `parallel_tool_calls` `max_completion_tokens` `modalities` `audio` `store` `safety_identifier` `web_search_options` `metadata` `include_reasoning` `probe_zzz` |

> 注意两层区别：“在结构体”只意味着**送达了解码器**（如 `stop` / `top_p`），仍然可能不执行；
> “不在结构体”就可以直接定为不支持，无需再试。

**`tool_choice` 只接受字符串** —— 这是实测撞出来的结构约束。传对象形式：

```json
{"tool_choice": {"type": "function", "function": {"name": "get_weather"}}}
```

→ `400`，原文：

```
Unmarshal chat params failed with error: json: cannot unmarshal object
into Go struct field Request.tool_choice of type string
```

> 这条错误同时暴露了两件事：① 后端是 **Go**（`json.Unmarshal` 报错风格）；
> ② 该字段在 Go 结构体里是 **`string`** 类型 → 只支持 `"auto"` / `"none"` / `"required"`。

## 六、响应：SSE 协议详解

### 6.1 传输层（实测响应头）

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Transfer-Encoding: chunked
Connection: close
Server: APISIX/3.9.1
Traceid: bb4989aea52a19614a91596fbe064025
X-Request-Id: 6657da6d-65d7-4fef-954b-994493a04bac
X-User-Id: 887e22c0-32df-4935-8811-226031b6d12d
EO-LOG-UUID: 12725329429203331626
```

- `Cache-Control: no-cache` + `chunked`：**不要**做响应缓冲，逐块读。
- `X-User-Id` 是服务端**回填**的账号标识，可作为「令牌被识别为谁」的自证。
- `Traceid` / `EO-LOG-UUID` 提工单时有用。

### 6.2 帧语法（官方实现 `parseSSELine`，逐条语义）

出处：`agent-client-protocol/.../transport/streamable-http.ts`。**这是权威解析规则**：

```js
function parseSSELine(line, currentEvent) {
  if (line === "")                      // ① 空行 = 派发
    return currentEvent.data
      ? { event: { type: currentEvent.type || "message",
                   data: currentEvent.data, id: currentEvent.id },
          reset: true, isComment: false }
      : { reset: true, isComment: false };
  if (line.startsWith(":"))             // ② 冒号开头 = 注释（心跳），忽略
    return { reset: false, isComment: true };
  const colonIndex = line.indexOf(":"); // ③ 找第一个冒号
  if (colonIndex === -1) return { reset: false, isComment: false };
  const field = line.slice(0, colonIndex);
  let value = line.slice(colonIndex + 1);
  if (value.startsWith(" ")) value = value.slice(1);   // ④ 只剥一个前导空格
  switch (field) {
    case "event": …                       // 本接口不用 event 字段
    case "data":  currentEvent.data = (currentEvent.data || "") + value;  // ⑤ 直接拼接
    case "id":    currentEvent.id = value;
  }
}
```

**五个必须记住的点**：

1. **空行才是帧终止符**。按行读、遇到空行才派发。
2. `:` 开头是注释 —— **本接口的心跳就是 `: heartbeat`**，必须忽略而不是解析 JSON。
3. 字段名与值之间**只剥一个空格**：`data:  {"x"}`（冒号后两个空格）的值会以 `{` 之外的
   一个多余空格开头。本接口格式规范，实测统一是 `data: {...}`。
4. **多行 `data:` 是直接拼接、不插换行**（注意这与 SSE 规范说的「用 `\n` 连接」不同）。本接口实测每帧只有一行 `data:`，所以不触发。
5. `event` 字段本接口**不发**，解析器默认 `type = "message"`。

**超时参数**（官方默认值，可作实现参考）：
`heartbeatTimeout = 60000`（60 秒无心跳判死）、`connectionTimeout = 30000`、`postTimeout = 30000`。

### 6.3 帧序（实测，`glm-5.3`，21 个内容帧）

```
┌─ 连接建立 ─────────────────────────────────────────────┐
│  HTTP 200  Content-Type: text/event-stream             │
└────────────────────────────────────────────────────────┘
   │
   ├─ : heartbeat                       ← 注释帧，SSE 注释行，忽略
   ├─ data: {chunk}   ← delta.reasoning_content="The"     ← 思维链开始
   ├─ (空行)
   ├─ data: {chunk}   ← reasoning_content 继续…           × N
   ├─ (空行)
   ├─ data: {chunk}   ← delta.content="" 但 reasoning 在走
   ├─ (空行)
   │   … 推理阶段的帧 content 恒为 "" ，全部内容走 reasoning_content
   ├─ data: {chunk}   ← delta.content="4"                 ← 正文开始
   ├─ (空行)
   ├─ data: {chunk}   ← content 继续…
   ├─ (空行)
   ├─ data: {chunk}  finish_reason=""   usage=null        ← 末前的空 delta
   ├─ (空行)
   ├─ data: {chunk}  finish_reason="stop"  usage={...}    ← ★ 收尾帧（内联 usage）
   ├─ (空行)
   └─ data: [DONE]                       ← 流结束哨兵
   └─ (空行)
```

**实测计数**：47 行 = 23 个 `data:` 行（22 chunk + 1 `[DONE]`）+ 23 个空行 + 1 个 `: heartbeat`。

> **注意末前那帧**：`delta` 全空、`finish_reason: ""`、`usage: null`。
> 这是网关的「准备收尾」信号，客户端应当**跳过**（不产生任何输出）。

### 6.4 原文样例（逐行，**实测原样**）

**心跳 + 首帧**：

### 6.5 chunk 帧结构（TypeScript 风格定义）

**每一帧 `data:` 的 JSON 结构**：

```ts
interface ChatCompletionChunk {
  id: string                          // 一次补全内所有帧相同
  object: "chat.completion.chunk"     // 恒为此字面量
  model: string                       // 回显实际模型，如 "glm-5.3"
  created: number                     // Unix 秒，所有帧相同

  choices: Array<{
    index: number                     // 通常 0
    delta: Delta                      // 见 6.6
    logprobs: null                    // 恒 null
    finish_reason: "" | "stop" | "length" | "tool_calls"   // ★ 进行中是 ""
  }>

  usage: Usage | null                 // ★ 非收尾帧恒 null；收尾帧为完整对象（见 6.8）
}
```

| 字段 | 类型 | 实测值 / 说明 |
| --- | --- | --- |
| `id` | string | 一次补全**所有帧相同**，如 `b1910a20-c69f-42d6-a5f3-e3b357df690a` |
| `object` | string | 恒为 `"chat.completion.chunk"` |
| `model` | string | 回显实际模型，如 `"glm-5.3"` |
| `created` | number | Unix **秒**，所有帧相同（注意：**是秒，不是毫秒**） |
| `choices` | array | 通常长度 1（`n=1`） |
| `choices[].index` | number | `0` |
| `choices[].delta` | object | 见 6.6（**每帧 7 键齐全**） |
| `choices[].logprobs` | null | 恒 `null` |
| `choices[].finish_reason` | string | **`""` 表示未结束**，不是 `null`；见 6.7 |
| `usage` | object \| null | 非收尾帧恒 `null`；收尾帧为完整对象，见 6.8 |

### 6.6 `delta` 的字段（**本接口比 OpenAI 多**）

实测每帧 `delta` 都带全 7 个键：

```json
{
  "role": "assistant",
  "content": "",
  "reasoning_content": "The",
  "function_call": null,
  "refusal": "",
  "tool_calls": [],
  "extra_fields": null
}
```

| 键 | 语义 | 实测形态 |
| --- | --- | --- |
| `role` | 角色 | 首帧起恒为 `"assistant"`（**每帧都发**，非仅首帧） |
| `content` | 正文增量 | 推理阶段恒 `""`；正文阶段为增量文本 |
| **`reasoning_content`** | **思维链增量**（本接口特有） | 字符串，与 `content` **互斥地先后出现** |
| `function_call` | 旧式函数调用字段 | 普通帧为 `null`；**收尾帧变成 `{"name":"","arguments":""}`**（恒为空串，无信息量） |
| `refusal` | 拒答文本 | 恒 `""`（空串，非 `null`） |
| `tool_calls` | 工具调用增量 | 未触发时恒 `[]`；触发时**非空数组**，见 **6.12** |
| `extra_fields` | 厂商扩展 | 恒 `null` |

**`delta` 的键在每一帧都齐全**（含值为 `""` / `[]` / `null` 的），
**不是** OpenAI 那种「按需只出现变化的键」。→ 客户端判空要判**值**，不能判键是否存在。

> **`reasoning_content` 是额外字段**：OpenAI 官方协议没有它。
> 标准 OpenAI 客户端会直接忽略它 —— 这是安全的；但如果你想展示思维能力，就得显式读它。
>
> 官方客户端还处理了一个兼容坑（`app.asar` @30228924 注释原文）：
> *「部分 provider（如 BYOK 下的 step-3.7-flash）每个 delta 里同时带
> `reasoning_content` 和 `reasoning`，且文本相同。两个都累加会让每个片段翻倍
> （"TheThe user…"）。**优先用 `reasoning_content`，仅当该帧没有它时才回退 `reasoning`**。」*
>
> → **实现建议**：`reasoning_content` 与 `reasoning` 二选一，**不要同时累加**。

### 6.7 `finish_reason` 语义（**与 OpenAI 不同**）

| 阶段 | 本接口 | OpenAI 官方 |
| --- | --- | --- |
| 流进行中 | **`""`**（空字符串） | `null` |
| 正常结束 | `"stop"` | `"stop"` |
| 超 `max_tokens` | `"length"`（**已实测**） | `"length"` |
| **触发函数调用** | `"tool_calls"`（**已实测**，见 6.12） | `"tool_calls"` |

> 实测出现的取值共 3 个：`"stop"` / `"length"` / `"tool_calls"`。
> 用 `in ("stop","length","tool_calls","content_filter")` 判定最稳。

⚠️ **客户端要按 `!== "stop" && !== ""` 或在收尾帧判断，不能写 `finish_reason !== null`** ——
本接口全程不为 `null`，那个判断永远为真，会导致「把每个中间帧当成结束」。

推荐判定式：

```python
if chunk["choices"][0]["finish_reason"] in ("stop", "length", "content_filter"):
    # 这才是真正的收尾帧
```

**实测记录（`length` 分支）** —— `max_tokens: 20` 触发输出截断：

```
帧数        : 10   哨兵 [DONE]: True
finish      : length
耗时        : 2.1s
tokens      : prompt=17 completion=20 total=37
thinking    : 19 tokens
credit 消耗 : 0.01
```

两个要点：

1. **`finish_reason` 变成 `"length"` 时，`usage` / `[DONE]` 一切照常** ——
   网关不会因为截断就省略收尾帧，所以 `length` 也要走正常收尾路径
   （不要当成错误而丢弃已收到的内容）。
2. **`completion_tokens` 精确等于 `max_tokens`（20）** —— 说明该字段以实际生成量为准，
   可作为「是否被截断」的旁证。
3. 附带验证：此时**同样收到 `usage`**，说明 `usage` 与 `finish_reason` 的取值无关。

收尾帧内联，字段比 OpenAI 多得多：

```json
{
  "prompt_tokens": 20,
  "completion_tokens": 65,
  "total_tokens": 85,
  "completion_tokens_details": {
    "accepted_prediction_tokens": 0,
    "audio_tokens": 0,
    "reasoning_tokens": 57,
    "rejected_prediction_tokens": 0,
    "cached_tokens": 0

  "prompt_tokens_details": {
    "accepted_prediction_tokens": 0,

    "reasoning_tokens": 0,

**标准 OpenAI 字段**：`prompt_tokens`、`completion_tokens`、`total_tokens`、
`completion_tokens_details.reasoning_tokens`、`prompt_tokens_details.cached_tokens`。

**本接口特有**：

| 字段 | 语义 |
| --- | --- |
| **`credit`** | **本次消耗的积分数**（实测 `0.06`；短请求可为 `0`） |
| `completion_thinking_tokens` | 思维链 token 数（与 `reasoning_tokens` 实测同值 57） |
| `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 提示缓存命中/未命中 |
| `cache_read_input_tokens` / `cache_creation_input_tokens` / `prompt_cache_write_tokens` | Anthropic 风格的缓存字段（对齐用） |
| `cached_tokens`（顶层） | 冗余镜像 |

> **关键差异**：**`usage` 挂在 `finish_reason` 那一帧上，且 `choices` 非空**。
> OpenAI 官方在 `include_usage: true` 时是**单独一帧、`choices: []`**。
> 所以**不能**写「找 `choices` 为空的帧拿 usage」——这里永远找不到。
>
> 实测：**不开 `stream_options.include_usage` 也照样有 usage**（有用时含 1 个 usage 帧）；
> 显式开启后同样只有 1 帧，**行为无差别**。

### 6.9 结束哨兵

```
data: [DONE]
```

- **纯字面量，不是 JSON** —— 直接 `JSON.parse` 会抛异常。
- 处理顺序：**先判 `[DONE]`，再 parse**。
- 收到后应停止读取，但**不要立即丢弃已累积内容**（部分实现会在 `[DONE]` 后仍留缓冲）。
- 官方 OpenAI SDK 的写法可参考（`app.asar` @96013475）：
  ```js
  if (sse.data.startsWith('[DONE]')) { done = true; continue; }
  ```

### 6.10 客户端参考实现（Python 标准库，可直接跑）

```python
import json, urllib.request

def chat_stream(url, headers, body):
    """产出 ('reasoning', text) / ('content', text) / ('usage', dict)"""
    req = urllib.request.Request(url, data=json.dumps(body).encode(),
                                 headers=headers, method="POST")
    with urllib.request.urlopen(req, timeout=570) as resp:
        assert resp.headers.get("Content-Type", "").startswith("text/event-stream")
        buf = {"data": ""}
        for raw in resp:                                  # 逐行读，别 read()
            line = raw.decode("utf-8", "replace").rstrip("\r\n")

            # ① 空行 = 派发
            if line == "":
                if not buf["data"]:
                    continue
                payload, buf["data"] = buf["data"], ""
                if payload.strip() == "[DONE]":            # ② 先判哨兵
                    break
                try:
                    chunk = json.loads(payload)
                except ValueError:
                    continue                               # 容错：坏帧不致命
                for ch in chunk.get("choices") or []:
                    d = ch.get("delta") or {}
                    if d.get("reasoning_content"):
                        yield ("reasoning", d["reasoning_content"])
                    elif d.get("reasoning"):               # 二选一，勿同时累加
                        yield ("reasoning", d["reasoning"])
                    if d.get("content"):
                        yield ("content", d["content"])
                    if d.get("tool_calls"):
                        yield ("tool_calls", d["tool_calls"])   # 合并规则见 6.12
                    if ch.get("finish_reason"):
                        yield ("finish", ch["finish_reason"])
                if chunk.get("usage"):
                    yield ("usage", chunk["usage"])
                continue

            # ③ 注释帧（心跳）忽略
            if line.startswith(":"):
                continue

            # ④ 字段解析：只剥一个前导空格
            i = line.find(":")
            if i == -1:
                continue
            field, value = line[:i], line[i + 1:]
            if value.startswith(" "):
                value = value[1:]
            if field == "data":
                buf["data"] += value                       # 多行 data 直接拼接
```

> **上面是「拆帧」部分**（把 SSE 字节流变成事件）。
> **`tool_calls` 的合并**属于「状态」部分，见 **6.12**；
> 完整可运行的实现是本目录的 **`workbuddy_chat.py`**（436 行，仅标准库），
> 已实测跑通 `tools` 分支：
>
> ```bash
> python workbuddy_chat.py --tools @tools.json --show-tools "查一下北京和上海的天气"
> ```
>
> 输出（实测）：
>
> ```
> [函数调用 #0]  id=call_1ece1f0c…  name=get_weather
>   arguments : {"city": "北京", "unit": "c"}      ← 拼接后解析成功
> [函数调用 #1]  id=call_518fdca8…  name=get_weather
>   arguments : {"city": "上海", "unit": "c"}
> finish=tool_calls   函数调用=2 个   credit=0.05
> ```

### 6.11 九个坑（逐条实测确认）

| # | 坑 | 后果 | 正解 |
| --- | --- | --- | --- |
| 1 | 不传 `stream: true` | `400 / 11101` | 必须显式 `true` |
| 2 | 用 `resp.read()` 一次性读完 | SSE 永不结束或长时间空等 | **逐行迭代** |
| 3 | 对 `data: [DONE]` 做 `JSON.parse` | 抛异常，可能中断整个流 | 先判字符串 |
| 4 | 判 `finish_reason is None` 来找结束 | 永远不成立 → 误把中间帧当代结束 | 判 `in ("stop","length","tool_calls",…)` |
| 5 | 找 `choices == []` 的帧取 `usage` | 找不到，用量统计恒为空 | usage 在 `finish_reason` 那帧上 |
| 6 | 把 `: heartbeat` 当 JSON 解析 | 每 60 秒左右报一次错 | `startswith(":")` 直接跳过 |
| 7 | `reasoning_content` 与 `reasoning` 同时累加 | 思维链文本**逐段翻倍** | 优先 `reasoning_content`，否则 `reasoning` |
| 8 | 401 时无脑 `JSON.parse` | 响应是 **HTML**，解析崩溃掩盖真实原因 | 先看 `Content-Type` |
| 9 | `tool_calls` 按数组下标合并 / 逐帧解析 `arguments` | 多调用串号、参数解析必失败 | 按 `index` 合并 + 拼接后再解析，见 **6.12** |

**另外三条运营经验**（来自官方实现）：

- 心跳超时按 **60 秒**判死（`heartbeatTimeout = 60000`）。
- 上游总超时 **570 秒**（`upstreamTimeoutMs = 570000`）。
- 401 要「刷新后重试一次」，且**失败时原样透传上游 401**，不要自造错误。

### 6.12 `tool_calls` 的流式结构（**实测，函数调用怎么流**）

这一块是本接口最容易被写错的结构，因为 **OpenAI 风格的增量合并规则有三个坑**。

**实测逐帧**（`tools` 里放一个 `get_weather`，让它查北京 + 上海两个城市）：

```
[16] delta.tool_calls=[{"id":"call_86f5cde3…","type":"function",
                        "function":{"name":"get_weather","arguments":""},"index":0}]
[17] delta.tool_calls=[{                          "type":"function",
                        "function":{"name":"",          "arguments":"{\"city\": \"北京"},"index":0}]
[18] delta.tool_calls=[{                          "type":"function",
                        "function":{"name":"",          "arguments":"\", \"unit\": \"c"},"index":0}]
[19] delta.tool_calls=[{                          "type":"function",
                        "function":{"name":"",          "arguments":"\"}"},"index":0}]
[20] delta.tool_calls=[{"id":"call_d9783a04…","type":"function",
                        "function":{"name":"get_weather","arguments":""},"index":1}]   ← 第二个调用
[21] ... [23] 同 17-19，index=1
[24] delta.function_call={"name":"","arguments":""}
     finish_reason="tool_calls"      usage.credit=0.05 total=262
data: [DONE]
```

**结构定义**：

```ts
interface DeltaToolCall {
  index: number                 // ★ 合并键，0 起
  id?: string                   // ★ 只在「该调用的第一帧」出现
  type?: "function"             // ★ 只在第一帧出现
  function?: {
    name?: string               // ★ 只在第一帧有值；续帧是 ""
    arguments?: string          // ★ 每帧一个 JSON 字符串片段，须拼接
  }
}
```

**四条合并规则（照做就不会错）**：

| # | 规则 | 违反的后果 |
| --- | --- | --- |
| 1 | **按 `index` 合并，不按数组下标** | 一帧一个 `tool_calls` 元素，按位置取会串号 |
| 2 | **`id` / `type` / `function.name` 只在首帧**；续帧这些字段缺失或为 `""` | 每帧都覆盖 → `name` 被 `""` 抹掉 |
| 3 | **`function.arguments` 是流式 JSON 字符串片段**，须**先拼接再 `json.loads()`** | 逐帧解析必然失败（`{"city": "北京` 不是合法 JSON） |
| 4 | **收尾帧 `finish_reason="tool_calls"`**，`usage` 照常内联 | 判 `"stop"` 会漏掉函数调用分支 |

**参考实现**：

```python
calls = {}                                  # index -> {"id":…, "name":…, "args":""}
for tc in (delta.get("tool_calls") or []):
    i = tc["index"]                          # ★ 规则 1
    slot = calls.setdefault(i, {"id": None, "name": None, "args": ""})
    if tc.get("id"):                         # ★ 规则 2：只在首帧覆盖
        slot["id"] = tc["id"]
    fn = tc.get("function") or {}
    if fn.get("name"):                       # ★ 规则 2：别用 "" 覆盖
        slot["name"] = fn["name"]
    if fn.get("arguments"):
        slot["args"] += fn["arguments"]      # ★ 规则 3：先拼接
# 收尾后再统一解析
for i, s in sorted(calls.items()):
    s["parsed_args"] = json.loads(s["args"])  # {"city": "北京", "unit": "c"}
```

**实测观察到的两个附带事实**：

1. 触发函数调用时，**模型仍会先输出正文**（`content="我来帮您查询北京和上海的天气情况。"`）
   再进入 `tool_calls` 帧 —— 所以不能假定「有 tool_calls 就没有 content」。
2. `delta.function_call`（旧式字段）在收尾帧被填成 `{"name":"","arguments":""}`，
   **信息为空**；真正的内容在 `tool_calls` 里。→ **用 `tool_calls`，忽略 `function_call`。**

### 6.13 SSE 字段全集、心跳、交付边界

**字段**：本接口只用 `data:` 与 `:`（注释，仅 `: heartbeat`）。
**不出现** `event:` / `id:` / `retry:`。

**心跳**：只在流开始出现 **1 次**，不是周期性保活。
（实测长输出 1404 帧 / 11.4s，最大行间间隔 0.10s，全程未再发心跳。）

**交付边界**：HTTP 层不保证一次读取正好一行 —— `data: {...}` 可能被切在任意字节位置。
**客户端必须自行累积到换行符再解析**（行缓冲实现见 6.2 与 6.10）。

**`n` 被静默忽略**：

| 请求 | `choices` 长度 | `index` 取值 |
| --- | --- | --- |
| `n=1` | `[1]` | `{0}` |
| `n=2` | **`[1]`** | **`{0}`** |

**仍未验证**：HTTP 200 之后、流中途出错的表现 —— 未构造出该场景，官方产物中也无对应处理分支。

## 七、错误模型

### 7.1 统一信封结构

**成功**（`code: 0`）：

```ts
{
  code: 0
  msg: "OK"
  requestId: string
  data: object          // 各接口自己的数据体
}
```

**失败**（业务层，`Content-Type: application/json`）：

```ts
{
  code: number                       // 业务码（见 7.2；★ 通用码，勿按码判语义）
  msg: string                        // 英文原文，排障用
  requestId: string                  // 提工单时带这个
  extError?: {                       // 仅部分错误带（如 11133），定位到具体字段
    code: string                     // "400002"
    message: string
    param?: string                   // ★ 出错字段名，如 "messages"
    type?: string                    // "invalid_request_error"
    StatusCode?: number
    Request?: null
    Response?: null
  }
  displayMsg?: {                     // ★ 三语展示文案，直接给用户看
    en: string
    zh: string
    "zh-hant": string
  }
  displayTips?: { en: string; zh: string; "zh-hant": string }   // 三语补充建议
  actions?: string[]                 // 建议动作枚举，见下
}
```

**`actions` 实测出现过的取值**（共 4 个）：

| 值 | 含义 |
| --- | --- |
| `RETRY` | 可直接重试 |
| `SUBMIT_FEEDBACK` | 建议提交反馈 |
| `SWITCH_MODEL` | 换模型 |
| `NEW_CONVERSATION` | 新建会话 |

> **`displayMsg` / `displayTips` 应直接展示给用户** —— 别自己硬编码错误提示。
> 官方就是这么做的，文案比我们编的准确。

### 7.2 实测错误码表

| HTTP | code | 触发条件 | 原文 msg | actions |
| --- | --- | --- | --- | --- |
| **400** | **11101** | ① 未传 `stream: true`<br>② **请求体字段类型不符**（如 `tool_choice` 传对象） | ① `Non-stream chat request is currently not supported`<br>② `Unmarshal chat params failed with error: json: cannot unmarshal object into Go struct field Request.tool_choice of type string` | `RETRY`, `SUBMIT_FEEDBACK` |
| **400** | **11102** | 模型不可用（**三种语义，见 7.4**） | ① `model [X] service info not found`<br>② `model [X] is only available for authorized users`<br>③ `Invalid model [X]`（legacy `/v2/completions`） | `SWITCH_MODEL`, `SUBMIT_FEEDBACK`, `RETRY` |
| **400** | **11103** | 模型不是聊天模型（如目录里的图像模型） | `Backend [hunyuan-stream] is not supported` | — |
| **400** | **11133** | 参数被上游模型拒绝（如 `messages: []`） | `the request parameters were rejected by the model provider` | `SWITCH_MODEL`, `SUBMIT_FEEDBACK`, `NEW_CONVERSATION` |
| **401** | —（**无 JSON 信封**） | 缺 / 失效 `Authorization` | —（HTML） | — |

### 7.3 `11101` 是**通用码**，不能按码判语义

`11101` 至少出现在两类完全不同的场景：

| 场景 | msg |
| --- | --- |
| 未传 `stream: true` | `Non-stream chat request is currently not supported` |
| **字段类型不符**（`tool_choice` 传对象） | `Unmarshal chat params failed with error: json: cannot unmarshal object …` |

**同一码两义。** 所以：

- ❌ 写 `if code == 11101: 提示"必须用流式"` —— 类型错误会被误报成「需要流式」。
- ✅ 写 `if "Non-stream" in msg` 或直接展示 `displayMsg` + `msg`。

### 7.4 `11102` 也是**通用码**，三种语义（实测）

| msg | 真实含义 | 应对 |
| --- | --- | --- |
| `model [X] service info not found` | 模型 id 完全不存在 | 换模型 |
| `model [X] is only available for authorized users` | **模型存在，但当前账号无权使用** | 换模型，或申请授权 |
| `Invalid model [X]` | 该模型不属于这条路由（legacy `/v2/completions` 用文本模型时会这样） | 换模型 / 换路由 |

**实测样本**：`gpt-5.6-sol`、`gemini-3.5-flash` → 第②种。
→ **不要把 `11102` 一律报成「模型不存在」**，会把「没权限」误导成「拼错了」。

### 7.5 `code` 只用于分组，语义必须看 `msg`

以上两例（`11101` 两义、`11102` 三义）已足够说明。另有签到侧 `10001`
（「今天已签到」/「签到活动未开启」）。详见《认证与签到协议》第五节。

**客户端做法**：直接采用服务端返回的 `displayMsg` / `displayTips`，不要按 `code` 自造文案。

### 7.6 401 是网关层，不是业务层（结构与别处不同）

```http
HTTP/1.1 401 Authorization Required
Content-Type: text/html; charset=utf-8      ← ★ 不是 JSON
Server: APISIX/3.9.1
```

```html
<html><head><title>401 Authorization Required</title></head>
<body><center><h1>401 Authorization Required</h1></center>
<hr><center>openresty</center>...</html>
```

**结构上与其他错误完全不同**：没有 `code` / `msg` / `displayMsg`，是纯 HTML。
所以客户端必须**先看 `Content-Type` 再决定怎么解析** —— 见 6.11 坑 8。

### 7.7 签到接口的错误码不能类推

不要以为聊天与签到共用码表。签到侧的 `10001` 同样是**通用码**
（「今天已签到」/「签到活动未开启」），必须看 `msg` 区分。详见《认证与签到协议》第五节。

## 十、与 OpenAI 官方协议的差异对照

| 维度 | OpenAI 官方 | 本接口 | 影响 |
| --- | --- | --- | --- |
| 非流式 | 支持 | **不支持**（`11101`） | 必须用流式 |
| 进行中 `finish_reason` | `null` | **`""` 空字符串** | `!== null` 判断失效 ⚠️ |
| `usage` 位置 | 单独一帧、`choices: []` | **内联在 finish 帧、`choices` 非空** | 按 `choices==[]` 找 usage 必失败 ⚠️ |
| `usage` 触发 | 需 `stream_options.include_usage` | **默认就给** | 无需额外开启 |
| `delta.reasoning_content` | 无 | **有** | 忽略即兼容；要用则显式读 |
| `delta.refusal` | `null` \| string | **`""` 空字符串** | 判 `if refusal:` 仍安全 |
| `delta` 的键 | 按需只出现变化项 | **每帧 7 键齐全**（空值也是 `""`/`[]`/`null`） | 判空要判**值**，不是判键 ⚠️ |
| `delta.function_call` | 弃用字段 | 普通帧 `null`，收尾帧 `{"name":"","arguments":""}`（无信息） | **用 `tool_calls`，忽略它** |
| `delta.tool_calls` | 有 | **有，结构同形**（按 `index` 合并；`id`/`name` 只在首帧） | 合并规则见 6.12 |
| `tool_choice` | 字符串或对象 | **只接受字符串** | 传对象必 `400` ⚠️ |
| `delta.extra_fields` | 无 | 有（恒 `null`） | 忽略 |
| `usage.credit` | 无 | **有（本接口计费核心）** | 想算花费必须读它 |
| `usage.completion_thinking_tokens` | 无 | 有 | 冗余 |
| 错误信封 | `{"error":{...}}` | **`{code, msg, requestId, extError?, displayMsg?, displayTips?, actions?}`** | 错误处理要重写 |
| 错误码语义 | 按 HTTP 状态 | **`code` 是通用码，语义看 `msg`**（`11101` 两义） | 不能按码判分支 ⚠️ |
| 日志链路 | `x-request-id` | `Traceid` + `EO-LOG-UUID` + `X-Request-Id` | 提工单用 |

**给「想直接复用 OpenAI SDK」的人的结论**：

用官方 SDK **可以连**（chunk / tool_calls 结构兼容），但：
- **`usage` 会拿不到**（位置不同）
- **`finish_reason` 语义要自己兜**（`""` 而非 `null`）
- **错误对象结构完全不同**，SDK 的异常解析会失效
- `tool_choice` 传对象会被拒

中等规模以上建议自己写 SSE 消费（约 60 行，见 6.10）。
