Origin: <realm 对应 origin>
Referer: <realm 对应 origin>/

## 三、OAuth 登录（官方 `platform=CLI` 流程）

> 这是 WorkBuddy **官方 CLI 插件登录流程**，不是绕过。来源：`cmd/login/main.go`。

### 步骤 1 — 取授权 URL

```http
POST {upstreamBase}/v2/plugin/auth/state?platform=CLI
<第二节全部通用头>
body: {}
```

响应（统一信封 `{code,msg,data}`，`code=0` 取 `data`）：

```json
{ "state": "<服务端签发的 state>", "authUrl": "https://...（浏览器打开用）" }
```

无 PKCE，**state 由服务端签发**。

### 步骤 2 — 浏览器完成登录

把 `authUrl` 在浏览器里打开，用你自己的账号登录。**只需一次**。

### 步骤 3 — 换 token

```http
GET {upstreamBase}/v2/plugin/auth/token?state=<state>
<第二节全部通用头>
```

- **未完成登录**：业务 `code = 11217` 或 `12151`（**已验证**：桌面端
  `isLoginPollPending(envelope, 11217)` 与 `(envelope, 12151)` 双命中，官方把这两个码
  白名单视为「登录进行中」继续轮询；其他非 0 code 应直接报错），或 HTTP 5xx
- **完成登录**：`code = 0`，`data`：

```json
{ "accessToken": "...", "refreshToken": "...", "expiresIn": 5184000, "domain": "..." }
```

（**注意**：`login.sh` 里按 snake_case `access_token` 取值，而 `main.go` / `client.go` 按
camelCase `accessToken`。**两种都写进解析器做兼容**，别只认一种。）

### 步骤 4 — 取账号信息（uid 必需）

```http
GET {upstreamBase}/v2/plugin/login/account?state=<state>
<通用头> + Authorization: Bearer <accessToken>
```

```json
{ "uid": "...", "enterpriseId": "...", "nickname": "..." }
```

**`uid` 就是后面签到要用的 `X-User-Id`。**

## 四、令牌刷新（可长期免登录）

来源：`internal/upstream/client.go:895-975`（`RefreshToken`）。

```http
POST {upstreamBase}/v2/plugin/auth/token/refresh
<RefreshHeaders：按 auth 记录注入 domain/uid/enterpriseId 等>
X-Refresh-Token: <refreshToken>
X-Auth-Refresh-Source: plugin
body: 空
```

（后两个头为 app.asar 逆向实锤，asar @115914939、@115935110；会话日志
`~/.workbuddy/logs/2026-09-25/` 中该端点多次实际发生刷新。）

响应同步骤 3：`{accessToken, refreshToken, expiresIn, domain}`。

**实测事实（原注释明确记录）**：
- `expiresIn` 恒为 **5184000（60 天）**
- **两个 token 总是一起 rotate**，写回时必须同时更新两个
- 服务端**无 rotation 撤销**：并发双刷新拿到的新 token 都有效
- 超过 10 年的 `expiresIn` 视为脏数据，**保留旧过期时间**（否则 `ExpiresAt` 推到荒谬未来 → 永不刷新 → 真过期）

→ 有了 refresh_token，**日常签到不需要你再登录**，只有 refresh_token 本身失效才需重登。

## 五、每日签到

来源：`login.sh:78-110` + `client.go:1925`；官方构造已从 app.asar 逆向实锤
（asar @138107594 起 AuthService 签到服务类）。**2026-09-26 用完整头实测通过，401 问题关闭**：
`checkin-activity-status` 返回 HTTP 200 + `code=0`（连签天数/credit/签到日期表）；
`daily-checkin` 在当日已签时返回 HTTP 400 + `code=10001`（幂等成功场景）。
实测走的是 cn 域 `https://copilot.tencent.com`（Origin `https://www.codebuddy.cn`）——
**cn realm 路由同步验证生效**。此前 401 缺的就是下面的头。

```http
POST {endpoint}/v2/billing/meter/daily-checkin
Authorization: Bearer <accessToken>
Accept: application/json
Content-Type: application/json
X-User-Id: <uid>                                  ← 必需，缺则 401
X-Enterprise-Id: <enterpriseId>                   ← 企业账号才带（官方按 account.enterpriseId 非空才加）
X-Tenant-Id: <enterpriseId>                       ← 同上
X-Domain: <domain>                                ← 有则带
X-Device-Token: <turing 设备 token>               ← 见下方「图灵盾」；取不到时改发 X-Device-Token-Error，provider 缺失时两头部不带
body: {}
```

**伴生端点**（查签到活动状态，同一套头）：
`POST {endpoint}/v2/billing/meter/checkin-activity-status`，body `{}`。
实测响应（节选）：`{active, today_checked_in, streak_days, daily_credit: 100,
total_credits, checkin_dates[], week_progress[], season, activity_name}`。

> ⚠ **这个端点报的是「赛季活动」维度，不是日签本身**（2026-10-10 实测）。
> 上一季（第 9 季 Buddy加油站，2026-09-16 ~ 09-29）结束后，该端点返
> `active:false`、`season:0`、`start_time`/`end_time` 为空、**`today_checked_in:false` 且所有计数归零**，
> 但 `daily-checkin` 仍然能签成功并返 `credit=100`、`streak_days` 重新从 4 开始计数。
> 所以“今天到底签了没”**不能拿 `today_checked_in` 当唯一依据**；
> 以 `daily-checkin` 自己的响应为准：`code=0` 就是刚签上了，
> `code=10001` 且 `msg` 含「今天已签到」也是已签（幂等），两者都是成功。

**成功判定（官方实现）**：HTTP 200 且 `code == 0` 且 `data` 非空 → 返回 data；
否则返回 `{code, msg, requestId}`（code 缺省 -1，msg 缺省 "Checkin failed"）。

### 图灵盾设备 token（X-Device-Token）

- 来源：腾讯图灵盾（Turing Shield）风控 SDK，主进程后台**原生采集**，热路径规则是
  「采集只在后台进行，只影响后续请求」（asar @123064531 注释原文）；
- 注入链：Electron host 的 `createElectronHostAuth().getTuringDeviceToken()`
  → `getTuringDeviceTokenResultForRequest()`（`getTuringSdkService().getDeviceTokenForRequest()` 快照）
  → `authService.setTuringDeviceTokenProvider()`（asar @137162639）；
- **互斥头**（官方明说仿 CodeBuddy IDE）：拿到 token 发 `X-Device-Token`；
  拿到错误发 `X-Device-Token-Error`；两者都不存在（provider 未注入）则**头部一个都不带**
  ——即该头是 best-effort，不是硬前置。401 的真凶是缺 `X-User-Id` 等基础头。

**请求体是空对象 `{}`**，无任何业务参数（与本项目早先逆向一致）。

判定（来源：`cmd/signin/main.go` 的 `isAlready()`）：

| 情况 | 判据 |
| --- | --- |
| 成功 | `code == 0` |
| **已签到** | `code = 10001`，HTTP 400，msg「今天已签到，请明天再来」（实测 2026-09-26；旧记录的 `code=400` 说法作废） |
| 其它 | 视为失败 |

> 已签到**不算失败** —— 自动化里要按幂等成功处理，否则每天误报。

## 八、凭据来源：桌面端本地登录态（**关键，全部实测**）

这是整件事的正解 —— **不需要你手工提供任何令牌**。

### 位置

```
%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\
```

（`%APPDATA%` 亦有同名目录，作为回退）本机实测文件：

| 文件 | uid | domain | accessToken 形态 |
| --- | --- | --- | --- |
| `workbuddy-desktop.info` | `887e22c0…` | `www.workbuddy.cn` | **加密** `{$wbEncrypted:1, envelope:"…"}` |
| `workbuddy-desktop.2026-09-17T…info`（备份） | `887e22c0…` | `www.workbuddy.cn` | **明文** len=1334 ✅ |
| `workbuddy-desktop-ai.info` | `abca5883…` | `www.workbuddy.ai` | **明文** len=1382（另一个账号） |

### 加密形态说明（5.6.2 新增）

当前主文件的令牌**已加密**，取不出明文：

```json
"accessToken": { "$wbEncrypted": 1, "envelope": "<base64>" }
```
envelope 解 base64 后：
```json
{ "suite":1, "keyId":"9127dea1b44020a7", "nonce":"…", "authTag":"…", "ciphertext":"…" }
```

密钥材料在 `~/.workbuddy/keyblob`：
```json
{ "version":1, "keyId":"7ee32f57eb5befc4",
  "slots":[{ "type":"static-v1", "protectorKeyId":"9127dea1b44020a7", "wrapped":"…" }] }
```

（envelope 的 `keyId` 与 slot 的 `protectorKeyId` 一致。）
**本方案不去破解这层加密** —— 直接使用**带时间戳的明文备份文件**即可，无需解密。

> 这也是为什么某些参考实现「读 `auth.accessToken` 失败」：它们按明文写，
> 而当前版本已加密，`typeof token === "string"` 为假 → 静默跳过。

### 账号选择：**别按令牌有效期排序**

目录里可能同时有多个账号的明文文件。实测若按 `expiresAt` 取最新，会选中
global 号（其令牌 exp 更远），把 CN 主号挤掉 —— 而 global 号**没有签到活动**。

**正确做法**：读 `workbuddy-desktop.info` 的 `account.uid`（该字段即使令牌加密
仍是明文），那才是桌面端**当前登录**的账号。

### 两条实测纠正（与参考实现不同）

1. **`code=10001` 是通用码，不是「已签到」专用码**。
   同一码实测对应两种语义，必须看 `msg`：

   | msg | 含义 |
   | --- | --- |
   | `今天已签到，请明天再来` | 幂等成功 |
   | `签到活动未开启或已过期` | 真失败（如 global 号无活动） |

# 附录 A：聊天接口（Chat Completions）

> **状态：已实测跑通**（2026-09-26）。
> 完整规格见同目录 **《聊天接口规格.md》**（端点、头、请求体、SSE 逐帧详解、错误模型、差异对照）。
> 本附录只保留结论摘要。

## A.1 结论摘要

```http
POST https://copilot.tencent.com/v2/chat/completions      (CN)
Authorization: Bearer <accessToken>
Content-Type: application/json
{"model":"glm-5.3","stream":true,"messages":[{"role":"user","content":"说个你好"}]}
```

实测 `HTTP 200` + `text/event-stream`，98 行 SSE，3.6 秒，`[DONE]` 正常。
`usage.credit = 0.06`。

**三条硬性事实**：

1. **必须 `stream: true`** —— 不传 → `400 / code 11101`（`Non-stream chat request is currently not supported`）。
2. **`finish_reason` 进行中是 `""` 而非 `null`** —— 用 `!== null` 判结束会失效。
3. **`usage` 内联在 `finish_reason` 那一帧、且 `choices` 非空** ——
   按 OpenAI 那样「找 `choices: []` 的帧」永远找不到。

## A.2 请求头要求

| 头集 | 结果 |
| --- | --- |
| 仅 `Authorization` + `Content-Type` | **200** ✅ |
| + `x-requested-with` / `Accept` / `X-User-Id` + `X-Domain` | 200 |
| 官方全量头 | 200 |

**网关准入只看 `Authorization`。** `X-User-Id` 缺失也不影响 —— 服务端从令牌解析账号
（响应头会回显 `X-User-Id`，可自证）。

其余头的作用是**会话归属 / trace 链路 / 产品统计**：不带头不会失败，
但会让网关侧会话被拆散、链路断掉。**建议按官方全量携带，别当成失败原因。**

## A.3 错误码（与签到不共用）

签到侧 `code=10001` 是**通用码**（同一码两义：「今天已签到」/「活动未开启」），
必须看 `msg`。聊天侧另有自己的码表（实测）：

| HTTP | code | 含义 |
| --- | --- | --- |
| 400 | `11101` | 未传 `stream: true`；或**请求体字段类型不符**（同码两义，看 `msg`） |
| 400 | `11102` | 模型不存在 / 未接入 |
| 400 | `11133` | 参数被上游模型拒绝（带 `extError.param` 指明字段） |
| 401 | —（**HTML**，非 JSON） | 缺 / 失效 `Authorization` |

**且聊天错误体带三语 `displayMsg` / `displayTips` 与 `actions`**
（`RETRY`、`SWITCH_MODEL`、`SUBMIT_FEEDBACK`、`NEW_CONVERSATION`）——
应当直接展示给用户，不要自己硬编码提示文案。

> ⚠️ 聊天会真实消耗 `credit`（实测 `0.06`／次），不像签到是纯领取。
